### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge and verification gate.** Use the approved forge (gh by default) for reads. The parent assigns an independent verifier that did not write the patch, using a native task with explicit read-only or disjoint reproduction scope. Verify parent against head on the real surface with an available control skill or repo driver. Report PASS, PASS+NOTES, FAIL, or BLOCKED locally; posting externally needs authorization. A missing live driver, required lane, evidence receipt, or independent result is BLOCKED and stops merging. Green CI alone is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up only after explicit user authorization and host approvals.** Re-read head SHA, base, CI, required independent verdicts, and operator review gates immediately before each action. A stale or missing verdict stops the run. Merge one authorized PR at a time; a queued or auto-merge request is not a completed merge. Verify the forge reports merged into trunk before proceeding. Retarget, rebase, or push only when separately covered by authorization; never force by default. Revalidate changed code and merge results per step 3.
5. **Leave the stack unchanged while it lands.** Perform bounded read-only forge checks of the authorized frontier; never mutate topology to unstick a merge without authorization. Execute one bounded turn by default, checkpointing unfinished work for manual resume. Continue autonomously only under a user-explicitly enabled host Goal and its limits. A native cron wake requires both an exposed capability and user-approved schedule; otherwise resume manually. Never use the host CodeRabbit-only `/loop` as a pstack scheduler, and do not create daemons, cloud services, or event subscriptions.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
